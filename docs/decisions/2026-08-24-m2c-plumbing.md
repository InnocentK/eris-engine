# Engineering decision record — M2c: first live plumbing run, two defects fixed

Date: 2026-08-24 · Branch: `m2c-plumbing` → `main` · Tier: **contained**
(AGENTS.md "How work is done": spec → one worktree → ONE advisor pass → gate →
this record; no planner fan-out) · Implementer: Claude, one isolated worktree ·
Advisor: Codex via `codex exec -s read-only`, one pass.

## Why this milestone exists
Every path in the harness had been exercised hermetically only. The tiering
rule adopted in `053ea35` says cheap evidence comes before planning, so the
first M2c action was a live run rather than a design round:

`eval/run.py run --task-file eval/corpus/plumbing-control/task.json --arm single --panel claude`

The harness behaved correctly end to end (pack built, worker absence recorded,
scan ran, exit 3, no crash) and exposed two defects that no hermetic test could
have caught, because the fakes never execute a real CLI or a real `git`.

## Selected approach
**Defect A — `USER` is required for Claude authentication.** The from-`{}`
environment omitted it, so `claude` reported `Not logged in · Please run
/login` with valid credentials: a harness bug that reads as operator error.
Bisected on this machine (HOME+PATH+TMPDIR fails; +LOGNAME fails; +SHELL fails;
+USER succeeds). Fix: `launch.resolve_user()` from passwd only — an
environment-derived `getpass` answer counts as unresolved and `USER` is
omitted rather than invented; `build_env` writes it LAST and REFUSES a policy
`env` or a secret that names `USER`; `eris doctor` reports resolved/unresolved
and never prints the value.

**Defect B — a read-only git command disabled all verification.**
`git status --porcelain` refreshes `.git/index`; the tree-hash guard declared
`snapshot.violated` and refused every remaining verification command in the
run. Fix, both halves: Eris appends `--no-optional-locks` before every git
subcommand (models still may not supply globals), and the guard excludes
exactly `.git/index` and `.git/index.lock` — not `.git` wholesale, so a
command that rewrites refs, objects, HEAD, config or hooks is still caught
(each pinned by a test).

Also: the stale `~/.grok/auth.json` credential declaration removed (the Grok
CLI no longer creates it — found by `eris doctor`); `eval/corpus/
plumbing-control/` added as the first corpus entry, marked `"scored": false`
and honoured by both campaign discovery and the scorer; its snapshot is
GENERATED by `eval/make_control_snapshot.py` from a tracked `files/` directory
(a git repo cannot be committed inside another).

## Dissent and corrections (preserved)
- Advisor (one pass) confirmed the core of both fixes and found five items, all
  fixed: `USER` was policy-/secret-overridable and printed by the doctor;
  `plumbing-control` was documented unscored but would have been scored;
  `request_key` aliased an invalid model request instead of refusing it; the
  generator claimed portability while using POSIX shell tools; guard tests did
  not cover objects/HEAD/hooks/index.lock.
- Implementer's own corrections: the defect-B test only reproduces on a COPY
  of the repo (a freshly created repo's index stat cache still matches, so
  `status` has nothing to refresh) — its first version passed even with the fix
  removed; reading the `scored` flag by importing `eris.evidence` would have
  put `subprocess` on the scorer's import graph (caught by the existing AST
  guard), so the flag is read as plain JSON; `build_snapshot`'s default runner
  was bound at def time, the same hazard the repo already has a rule about.
- Synthesizer: my own first hypothesis for defect B (git writing `.git/index`
  during `ls-files`/`log`) was wrong; the ledger named `status --porcelain`.
- Rejected: excluding `.git` wholesale from the guard (would let a
  verification command rewrite refs unnoticed).

## Unresolved risks
1. The live run never got past `propose` (defect A), so the stages beyond it —
   critique, adjudicate, verification evidence reaching a judge — are still
   unproven live. `pack.incomplete` was a consequence of defect B and has NOT
   been re-checked live.
2. `eval/corpus` is excluded from ruff/mypy/coverage. Necessary (a generated
   snapshot duplicates module names, and planted-defect tasks must contain code
   the gates reject), but it is a real reduction in what the gate checks.
3. `resolve_user()` returns `None` on Windows by design, so `USER` is absent
   there; revisit with an explicit operator-supplied source, never the env path
   just closed.
4. The tracked policy still carries machine-specific absolute verify
   executables while machine-specific hashes live in a gitignored `pins.yaml`
   (recorded as M2c-2 in EVAL-PLAN with two candidate designs).
5. The control task's `mean()` raises on empty input, which a reviewer could
   defensibly call a defect; a flatter control may be better before the corpus
   grows around it.
